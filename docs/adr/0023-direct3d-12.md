# 0023. A Direct3D 12 backend beside Direct3D 11

- Status: Accepted
- Date: 2026-11-17

## Context

ADR 0013 built the DirectX backend on Direct3D 11 and said a Direct3D 12 backend could come as
another module. The plan for Phase 10 had named Direct3D 12. Direct3D 11 stays: it runs on any
Windows 10 PC and is a small backend. Direct3D 12 is what newer Windows features and the Xbox need,
so the engine should have both, chosen like any other backend.

## Decision

`modules/rhi/directx12` implements the graphics interface on Direct3D 12, feature level 11.0, as
the module `directx12`. The existing `directx` module stays Direct3D 11, under the same name, so
projects that list it are unchanged. A project picks one, or lists both as fallbacks:

```toml
[modules.windows]
rhi = ["vulkan", "directx12", "directx", "null"]
```

Settings under `[rhi.directx12]` mirror Direct3D 11's: `debug` turns the debug layer on (the
default in debug builds, when Windows' "Graphics Tools" feature is installed) and `software` uses
WARP.

### Same shaders as Direct3D 11

Direct3D 12 runs shader model 5.0 DXBC, so the backend loads the `.dxbc` files the Direct3D 11
backend does, and declares the same shader format. A game that lists both compiles its shaders
once. Shader model 6 and DXIL would need the DXC compiler and nothing the interface uses.

The registers are those of ADR 0013. One root signature serves every pipeline:

| Root parameter | Register | Holds |
|---|---|---|
| Root constant buffer view | `b0` | The uniform block of `set_uniforms`, written to per-frame upload memory |
| 32 root constants | `b1` | The push constants, as on Vulkan |
| Descriptor table, one view | `t0` | The texture of `bind_texture` |
| Static sampler | `s0` | Linear filtering, wrapping |

### What Direct3D 11 did, done here

- **Frames in flight.** Two frames are recorded ahead, each with its own command allocator and
  upload memory, and a fence says when the GPU is done with one.
- **Destroying.** A destroyed buffer, texture or pipeline is kept until the GPU has finished every
  frame submitted before, then released, and its texture's descriptor reused.
- **Uploads.** Buffers and textures live in GPU memory, copied there from upload memory through a
  command list the backend runs and waits for. They run on the frame queue, so a resource made
  while a frame is recorded is ready for it.
- **Mipmaps.** Direct3D 12 has no `GenerateMips`. The chain is made on the CPU when the texture is
  created, a 2x2 box filter per level, averaging sRGB colors in linear light, as GPUs do.
- **Constants between frames.** Direct3D 11's constant buffers keep their contents, so the last
  uniforms and push constants are set again at the start of every render pass.
- **GPU time and capture.** Timestamps are resolved into readback memory and read once the frame's
  fence passes. A screenshot copies the back buffer to readback memory and waits for that frame.

## Consequences

- The samples list `directx12` before `directx` on Windows, so a PC without Vulkan uses Direct3D 12
  and falls back to 11.
- Each sample with a DirectX check has a `_directx12_check` on the GPU, and those with a reference
  image a `_directx12_warp_check` that CTest runs on WARP. On an RTX 5080 they match the same
  references as Vulkan and Direct3D 11, and so do the WARP runs.
- `dream_rhi_directx12_tests` runs the backend on WARP, including a drawn triangle whose pixels
  show the uniforms, push constants and texture reached the shader, and fails on any error the
  debug layer reports.
- Mipmaps made on the CPU cost time when a large texture is created. Cooked textures with their
  own mipmaps, planned in Phase 11, would remove that.
- At most 4096 textures exist at once, the size of the descriptor heap.
- The debug layer needs the "Graphics Tools" feature. The checks so far ran without it.
